## 一、專題簡介

實踐大學高雄校區位在內門的山坡上，校園很大，建築分散，新生常常不知道從宿舍到教室要怎麼走、要走多久，也不知道哪條路比較不用爬坡。

這個程式把校園畫成一張地圖。使用者選好起點和終點，程式就會用**最短路徑演算法**找出路線並畫在地圖上，同時列出：

- 每一段要走幾公尺、往哪個方向、在哪裡左轉或右轉
- 總距離、預估步行時間
- 這條路要上坡、下坡幾公尺

另外還可以選「**最省力路線**」，讓程式避開陡坡；也可以把 **Dijkstra、A\*、Bellman-Ford 三種演算法**放在一起比較，看它們的差別。

## 二、功能介紹

### 1. 找路線
- 輸入起點、終點時會自動推薦地點，可以打代號（例如 `j`），也可以打部分名稱（例如「圖書」、「學生 停車」）
- 也可以直接點地圖：第一下是起點，第二下是終點
- 可以加一個途經點（可以不填），例如「宿舍 → 7-11 → 教室」
- 路線用紅線沿著道路畫出來，起點標綠色、終點標紅色
- 右邊面板列出每一站、每段距離、方向（↑↗→…）和轉彎（直走／左轉／右轉／迴轉）
- 「交換起點和終點」按鈕，可以馬上查回程

### 2. 坡度與最省力路線
- 每個地點都有海拔高度，結果會顯示整條路總共上坡、下坡幾公尺
- 每一段標出平均坡度，例如「上坡 6%」；坡度超過 8% 會標「陡」
- 勾選「**最省力路線（避開上坡）**」，程式會找比較不累的路，就算多走一點也沒關係
- 步行時間會把爬坡多花的時間算進去

### 3. 三種演算法比較
- 按「**比較三種演算法**」，同一段路會用 Dijkstra、A\*、Bellman-Ford 各找一次
- 三條路線用紅、藍、橘三種顏色疊在地圖上
- 右邊列出每種演算法的路線長度、處理了幾個地點、檢查了幾次道路、花了幾毫秒，最後寫出結論

### 4. 其他貼心設計
- 滑鼠移到地點上，會顯示全名和海拔
- 字型會自動挑電腦裡有的中文字型；Windows 螢幕縮放 125%、150% 時字也不會糊掉
- 地圖上的地點名稱有白底，不會和綠地、樹混在一起
- 螢幕比較小時（例如 1366 寬的筆電、投影機），地圖會自動縮小
- 地圖資料檔不見或格式錯誤時，會跳出視窗用中文說明原因，例如「JSON 格式有錯：第 12 行」

## 三、執行方式

**執行環境**：Python 3。只用 Python 內建的功能（`tkinter`、`json`、`heapq`、`math`、`time`、`unittest`），**不用安裝任何套件**。

在專題資料夾裡執行：

```
python main.py
```

執行測試：

```
python -m unittest discover -s tests
```

## 四、程式架構

程式分成「計算」和「畫面」兩部分。計算的部分（`core/`）完全不碰視窗，所以可以直接用 unittest 測試；畫面的部分（`ui/`）只負責顯示，不做計算。

```
campus-nav/
├── main.py              程式入口：讀地圖、開視窗；地圖讀不到時跳出中文錯誤說明
├── config.py            顏色、字型、視窗大小、走路速度、坡度係數等常數
├── data/
│   └── map_data.json    地點（nodes）與道路（edges）資料
├── core/                計算的部分
│   ├── graph.py         CampusGraph 類別：讀 JSON、建鄰接表、算每段路的花費（含坡度）、搜尋地點
│   ├── pathfinder.py    三種演算法：dijkstra、a_star、bellman_ford
│   └── route.py         檢查使用者的輸入、途經點、整理導航步驟、判斷方向和轉彎、
│                        算上下坡、比較三種演算法
├── ui/                  畫面的部分（tkinter）
│   ├── app.py           主視窗：把地圖和面板組起來，按下按鈕時呼叫 core 的函式
│   ├── map_view.py      地圖畫布：畫道路、地點、路線、圖例
│   ├── scenery.py       地圖裝飾：綠地、湖、建築、樹（只是好看，和找路線無關）
│   └── side_panel.py    右邊面板：輸入框、推薦清單、按鈕、結果顯示
├── tests/               unittest 測試（共 53 個）
└── docs/                網頁版（基本找路線功能，用 JavaScript 寫的展示版）
```

程式執行的流程：

```
main.py 讀 map_data.json → CampusGraph 建好鄰接表 → 開視窗
使用者選起點、終點，按「找路線」
  → route.plan_route 檢查輸入（找不到地點？起終點相同？）
  → pathfinder.dijkstra 找出路線
  → route.build_stops 整理成導航步驟，route.route_summary 算距離和上下坡
  → map_view 畫路線，side_panel 顯示結果
```

## 五、地圖資料

`data/map_data.json` 裡有 **74 個點、86 條道路**：

| 種類 | 意思 | 數量 |
|------|------|------|
| `building` | 建築（教學大樓、宿舍） | 12 |
| `facility` | 設施（球場、停車場、湖） | 18 |
| `gate` | 出入口 | 2 |
| `junction` | 路口（不能選，只用來連接道路） | 42 |

格式範例：

```json
{
  "nodes": [{"id": "J", "name": "J 圖書館…", "type": "building",
             "x": 528, "y": 150, "lat": 22.903067, "lng": 120.466088, "elevation": 155.6}],
  "edges": [{"from": "A", "to": "J", "distance_m": 45, "path": [[585, 175], [528, 150]]}]
}
```

| 欄位 | 用途 |
|------|------|
| `x`、`y`、`path` | 地圖上的像素座標，對照 1560×839 的校園地圖描出來，用來畫圖和判斷轉彎方向 |
| `distance_m` | 道路的實際長度（公尺），對照 Google 地圖換算，是演算法的權重 |
| `lat`、`lng` | 經緯度，A\* 用來估計「離終點的直線距離」，測試也用它檢查距離有沒有打錯 |
| `elevation` | 海拔（公尺），用來算坡度 |

**海拔資料的來源**：用每個地點的經緯度，查詢 Open-Meteo 提供的 Copernicus 地形資料（解析度 90 公尺）。因為 90 公尺一格太粗，同一格裡的高度完全一樣，跨格又會突然跳很多，所以每個地點再和周圍約 45 公尺的 8 個點加權平均，讓坡度比較平順。校園最高是 J 圖書館一帶（約 156 公尺），最低是北側出入口（約 82 公尺），高低差大約 74 公尺。這些數字是估計值，不是實地測量。

## 六、演算法說明

### 1. 用「圖」表示校園

把每個地點和路口當作「點」，每條道路當作「邊」，道路長度就是邊的「權重」。程式用**鄰接表**儲存：每個點記錄它連到哪些點、距離多少。道路是雙向的，所以兩個方向都要記。

### 2. Dijkstra 演算法（主要使用）

1. 起點距離設為 0，用 `heapq`（優先佇列）存放「待處理的點」
2. 每次從 heap 拿出目前離起點最近的點，這個點的最短距離就確定了
3. 看它的每個鄰居：如果「經過它再走過去」比原本知道的更近，就更新鄰居的距離，並記下是從哪裡走過來的
4. 拿出終點時就可以提早結束；再沿著「從哪裡走過來」的紀錄往回推，就得到完整路線

### 3. A\* 演算法

和 Dijkstra 幾乎一樣，差別在 heap 排序時多加上「**離終點的直線距離**」當作估計值。這樣會優先往終點的方向找，比較少去看反方向的地點。

因為沿著道路走一定不會比直線短，估計值不會超過真正的距離，所以 A\* 找到的路線一定和 Dijkstra 一樣短。

### 4. Bellman-Ford 演算法

不用 heap，而是每一輪把**全部道路**都檢查一遍，看能不能讓某個點變近；某一輪什麼都沒變，就代表找到答案了。它的好處是可以處理負的距離（Dijkstra 不行），缺點是要檢查的次數多很多。

### 5. 坡度：最省力路線

把每段路的權重從「距離」改成「**距離 + 上坡高度 × 8**」，下坡不加。

「8 倍」來自登山常用的**奈史密斯規則**：爬高 600 公尺所花的時間，大約等於在平地走 5 公里，換算下來爬 1 公尺大約等於走 8 公尺。

演算法本身不用改，只是權重換了，所以三種演算法都能找最省力路線。

例子：網球場 → F 教學大樓

| | 距離 | 要爬多高 |
|---|---|---|
| 最短路線 | 396 公尺 | 28 公尺 |
| 最省力路線 | 401 公尺 | 11 公尺 |

多走 5 公尺，可以少爬 17 公尺（大約 5 層樓）。在全部 992 組起點和終點裡，有 112 組的最省力路線和最短路線不一樣。

## 七、三種演算法比較結果

在校園地圖上，把 32 個可以選的地點兩兩配對，共 992 組，每種演算法各跑 20 次取平均：

| 演算法 | 平均處理地點 | 平均檢查道路次數 | 平均每次時間 | 路線是不是最短 |
|--------|-------------|-----------------|-------------|---------------|
| Dijkstra | 39.7 個 | 49.9 次 | 約 0.027 毫秒 | 是 |
| A\* | 21.0 個 | 28.5 次 | 約 0.032 毫秒 | 是 |
| Bellman-Ford | 10.9 輪 | 1511.8 次 | 約 0.287 毫秒 | 是 |

**觀察與結論**

1. **三種演算法找到的距離完全一樣**：992 組都一樣，測試程式有逐一比對。
2. **A\* 做的工作最少**：處理的地點和檢查的道路，大約只有 Dijkstra 的一半到六成，因為它會優先往終點方向找。
3. **但 A\* 的時間沒有比較快**：每一步都要用經緯度算一次直線距離（要用到三角函數），這張地圖只有 74 個點，省下來的工作抵不過多算的時間。地圖越大，A\* 的優勢會越明顯。
4. **Bellman-Ford 最慢**：每一輪都檢查全部道路，檢查次數是 Dijkstra 的 30 倍左右，時間大約慢 10 倍。
5. **所以這個專題用 Dijkstra 當主要的演算法**：寫法簡單、速度最快，校園地圖也沒有負的距離，不需要 Bellman-Ford。

## 十、遇到的困難與限制

- **距離和座標要自己描**：地圖上的道路是對照校園地圖一點一點描出來的，距離再對照 Google 地圖換算，所以寫了 `test_data.py` 自動檢查有沒有描錯或打錯。
- **海拔資料不夠細**：公開的地形資料 90 公尺才一格，看不出樓梯、小斜坡或建築底下整平過的地方，所以坡度只是估計。
- **判斷轉彎**：道路是彎的，不能只看兩個地點連成的直線，要看道路折線上最靠近路口的那一小段，才不會把轉彎誤判成直走。
- **不同電腦的字型**：微軟正黑體只有 Windows 有，所以程式會自動找其他中文字型。
